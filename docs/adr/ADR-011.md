# ADR 011: Supabase for Identity and Authentication

## Context
Aegion requires a secure identity and authentication layer that supports multi-user isolation. The application data (conversations, messages) needs to be strictly bound to authenticated users, protecting against IDOR vulnerabilities. Building and securing a custom authentication system from scratch (hashing, salting, JWT signing, password resets, OAuth integrations) carries high security risks and development overhead.

## Decision
We will use **Supabase Auth** as the identity provider for Aegion, decoupling authentication from the core application data.

- **Frontend**: Next.js will use `@supabase/ssr` to manage cookies and authenticate users. Only the public Supabase URL and Publishable Key will be exposed to the browser.
- **Backend (FastAPI)**: Will verify the Supabase JWT using the project's public JWKS (`.well-known/jwks.json`). The backend will validate the signature, algorithm (RS256), `aud`, `iss`, `exp`, and extract the `sub` claim.
- **Database (PostgreSQL)**: The `sub` claim will map to a local `users` table `id` (UUID). All application resources (conversations, messages) will foreign key to this `id`. The backend will automatically provision a local user record the first time a valid JWT `sub` is encountered.

## Consequences
### Positive
- **Security**: Supabase handles password hashing and secure token issuance. JWT verification is handled locally using industry-standard JWKS, minimizing secret sharing.
- **Scalability**: Can easily integrate OAuth providers later without backend changes.
- **IDOR Protection**: The `sub` claim is authoritative, enabling robust ownership checks for all application queries.

### Negative
- **Dependency**: Reliance on an external service (Supabase) for authentication, though it is open-source and can be self-hosted.
- **Sync Overhead**: Must maintain a local shadow `users` table to enforce foreign key constraints for application data.

## Status
Approved.
