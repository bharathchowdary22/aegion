# ADR-005: pgvector for Future RAG

## Decision
We will use the `pgvector` extension within PostgreSQL for our future Retrieval-Augmented Generation (RAG) vector storage needs, rather than adopting a dedicated vector database initially.

## Reason
By using `pgvector`, we can keep our infrastructure footprint small. It allows us to query standard relational data and vector embeddings in the same database, eliminating the need to sync data between a relational DB and a separate vector DB.

## Alternatives considered
- **Pinecone / Weaviate / Milvus**: Excellent dedicated vector databases, but they introduce another piece of infrastructure to manage and pay for. We can migrate to them if `pgvector` becomes a bottleneck.

## Consequences
- Our PostgreSQL instance must support the `pgvector` extension.
- May face scaling challenges at extremely large vector counts compared to specialized vector databases.
